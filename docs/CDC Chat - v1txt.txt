
L'ÉCRIN FRANÇAIS
Product Requirements Document (PRD)
Version 2.0
Document de référence du projet
Ce document définit la vision, les objectifs, les exigences fonctionnelles et techniques ainsi que les principes d'architecture de la plateforme L'Écrin Français.
Il constitue la référence unique pour le développement du produit, les évolutions futures et les outils d'intelligence artificielle (Claude Code notamment).

CHAPITRE 1 — Vision
1.1 Présentation
L'Écrin Français est une plateforme numérique permettant de concevoir, visualiser, personnaliser et commander des écrins, coffrets et présentoirs haut de gamme fabriqués en France.
L'objectif n'est pas uniquement de vendre des produits.
L'objectif est de proposer une expérience de conception sur mesure, où chaque client devient le concepteur de son propre écrin, accompagné par un configurateur intelligent.
Le site doit offrir une expérience digne des grandes maisons de luxe :
* simple ;
* élégante ;
* immersive ;
* rassurante ;
* techniquement irréprochable.

1.2 Vision long terme
À long terme, L'Écrin Français ne sera pas un site spécialisé dans un produit particulier.
Il deviendra une plateforme universelle de conception d'écrins haut de gamme.
Le moteur de configuration sera capable de prendre en charge différents univers sans modification profonde de son architecture.
Les premiers univers seront :
* ?? Vin
* ? Montres
* ?? Bijoux
L'architecture devra permettre d'ajouter ensuite :
* Spiritueux
* Stylos
* Maroquinerie
* Cadeaux d'entreprise
* Médailles
* Objets d'art
* Packaging de luxe
* Instruments de musique
* Tout autre univers nécessitant un écrin ou un présentoir personnalisé.
Le moteur de configuration restera identique.
Seules les données métier propres à chaque univers évolueront.

1.3 Les valeurs
Chaque décision devra respecter les valeurs suivantes.
Excellence
Le moindre détail compte.
Aucune fonctionnalité ne doit sembler "approximative".

Artisanat
Le configurateur doit mettre en valeur le savoir-faire humain.
Il ne doit jamais donner l'impression de vendre un produit industriel.

Élégance
Le design privilégiera :
* l'espace ;
* la sobriété ;
* la qualité des animations ;
* les transitions fluides ;
* des matériaux réalistes.

Innovation
L'Écrin Français doit devenir la référence du configurateur premium.
Chaque nouvelle fonctionnalité devra apporter une réelle valeur.

Pérennité
Le projet devra rester évolutif pendant de nombreuses années.
Aucune décision technique ne devra empêcher l'ajout de nouveaux univers.

CHAPITRE 2 — Les objectifs
Objectifs commerciaux
* Valoriser le savoir-faire de l'entreprise.
* Générer des demandes de devis qualifiées.
* Transformer les devis en commandes.
* Réduire les échanges répétitifs grâce à un configurateur complet.
* Offrir un service premium qui renforce la confiance.

Objectifs utilisateur
Le client doit pouvoir :
* découvrir les différents univers ;
* configurer librement un produit ;
* comprendre immédiatement les conséquences de chacun de ses choix ;
* visualiser son projet en 3D ;
* connaître son prix en temps réel ;
* sauvegarder son travail ;
* reprendre son projet depuis n'importe quel appareil après authentification ;
* partager son projet ;
* demander un devis ;
* transformer un devis en commande.

Objectifs techniques
L'application devra être :
* performante ;
* modulaire ;
* maintenable ;
* testable ;
* sécurisée ;
* évolutive.

CHAPITRE 3 — Les grands principes d'architecture
Principe n°1
Le projet est une plateforme.
Il ne doit jamais être pensé comme un simple configurateur de coffrets à vin.

Principe n°2
Chaque univers est une spécialisation.
Le moteur reste identique.

Principe n°3
Toutes les règles métier doivent être pilotées par les données.
Le moteur ne doit jamais contenir de logique spécifique au vin, aux montres ou aux bijoux.

Principe n°4
Toute nouvelle fonctionnalité devra être compatible avec les futurs univers.

Principe n°5
Chaque choix utilisateur devra être immédiatement visible.
Le configurateur doit fonctionner comme un dialogue permanent avec le client.

CHAPITRE 4 — Concept central
Le cœur de toute l'application est un objet unique :
Configuration
Une configuration représente un projet personnalisé créé par un client.
Elle est indépendante de l'univers.
Elle possède notamment :
* un identifiant unique ;
* un propriétaire ;
* un univers ;
* un produit ;
* un ensemble d'options ;
* un état d'avancement ;
* un prix ;
* un historique des versions.
Toutes les fonctionnalités du système reposent sur cet objet.

CHAPITRE 5 — Sauvegarde et synchronisation
Chaque utilisateur authentifié possède un espace personnel.
Les configurations sont enregistrées automatiquement dans le cloud.
Chaque configuration doit pouvoir être :
* reprise sur n'importe quel ordinateur ;
* reprise sur tablette ;
* reprise sur smartphone ;
* renommée ;
* dupliquée ;
* supprimée ;
* archivée ;
* restaurée ;
* partagée.
Le client ne doit jamais perdre son travail.
Le système effectue une sauvegarde automatique après chaque modification significative.
Chaque sauvegarde crée une nouvelle version de la configuration.
L'utilisateur peut revenir à une version antérieure si nécessaire.

CHAPITRE 6 — Les personas
Avant de développer la moindre fonctionnalité, il faut définir précisément les utilisateurs du système.
L'Écrin Français devra répondre aux besoins de plusieurs catégories de clients ayant des attentes très différentes.

Persona 1 — Le particulier
Profil
Le particulier souhaite offrir ou acquérir un écrin unique.
Il n'a aucune connaissance technique.
Il ne connaît pas les essences de bois, les techniques de fabrication ni les contraintes de conception.
Attentes
Il souhaite :
* être guidé ;
* comprendre facilement les choix proposés ;
* obtenir un résultat esthétique ;
* connaître immédiatement le prix ;
* être rassuré sur la qualité.
Le configurateur doit lui donner confiance.
Il doit avoir l'impression d'être accompagné par un artisan.

Persona 2 — Le collectionneur
Ce client possède plusieurs montres, bouteilles ou bijoux.
Il recherche :
* une finition irréprochable ;
* des matériaux nobles ;
* une personnalisation poussée.
Il est souvent prêt à investir davantage.
Le configurateur devra lui proposer davantage d'options avancées.

Persona 3 — Le professionnel
Exemples :
* domaine viticole ;
* horloger ;
* joaillier ;
* entreprise.
Ses attentes sont différentes.
Il souhaite :
* créer plusieurs projets ;
* retrouver facilement ses anciens projets ;
* partager un projet avec ses collaborateurs ;
* obtenir rapidement un devis.

Persona 4 — L'artisan
Il utilise le back-office.
Il doit pouvoir :
* retrouver un client ;
* ouvrir une configuration ;
* comprendre immédiatement les choix du client ;
* modifier certains paramètres ;
* communiquer avec le client ;
* transformer une demande en fabrication.

Persona 5 — L'administrateur
Il gère :
* les univers ;
* les matériaux ;
* les essences ;
* les tarifs ;
* les promotions ;
* les utilisateurs ;
* les commandes.
Il ne doit jamais intervenir directement dans la base de données.
Toutes les opérations devront être réalisables depuis le back-office.

CHAPITRE 7 — Parcours utilisateur
Le parcours client constitue un élément essentiel de l'expérience.
Il doit être fluide.
À aucun moment le client ne doit avoir l'impression d'utiliser un logiciel complexe.

Découverte
Le visiteur arrive sur la page d'accueil.
Le site présente :
* les valeurs de L'Écrin Français ;
* les différents univers ;
* des réalisations ;
* des témoignages ;
* les avantages du sur-mesure.
Objectif :
Donner envie de créer son propre écrin.

Choix de l'univers
Le client sélectionne un univers :
* Vin
* Montres
* Bijoux
Chaque univers possède :
* son identité visuelle ;
* ses matériaux ;
* ses options ;
* ses contraintes.
Le moteur de configuration reste identique.

Création d'une configuration
Une nouvelle configuration est créée.
Elle reçoit immédiatement :
* un identifiant unique ;
* une date de création ;
* un propriétaire (si connecté) ;
* un statut.

Configuration
Le client personnalise progressivement son projet.
Chaque modification :
* met à jour le modèle 3D ;
* recalcule le prix ;
* vérifie les contraintes de fabrication ;
* déclenche une sauvegarde automatique.
Le configurateur ne doit jamais bloquer le client.
En cas d'incompatibilité, il explique clairement le problème et propose des solutions.

Sauvegarde automatique
Cette fonctionnalité devient centrale.
Le client ne doit jamais avoir à cliquer sur "Enregistrer".
Le système enregistre automatiquement :
* après une modification importante ;
* avant une fermeture de session ;
* avant un changement d'univers ;
* avant une déconnexion.
Chaque sauvegarde crée une nouvelle version.

Synchronisation
Le client peut commencer un projet :
* au bureau ;
le poursuivre :
* chez lui ;
puis le modifier :
* sur une tablette.
Il retrouve exactement :
* les mêmes matériaux ;
* les mêmes textures ;
* les mêmes dimensions ;
* les mêmes images ;
* le même angle de caméra 3D (si cela a un intérêt) ;
* les mêmes annotations.

Demande de devis
À tout moment :
le client peut demander un devis.
Le devis contient :
* le résumé complet de la configuration ;
* des vues 3D ;
* les caractéristiques ;
* le prix estimatif ;
* les délais.

Commande
Une configuration peut être transformée directement en commande.
Aucune ressaisie ne doit être nécessaire.

CHAPITRE 9 — Architecture générale de la plateforme
9.1 Principes fondamentaux
L'architecture de L'Écrin Français doit respecter les principes suivants :
* Modularité : chaque fonctionnalité est indépendante.
* Extensibilité : un nouvel univers s'ajoute sans modifier le moteur.
* Maintenabilité : un développeur découvrant le projet doit comprendre rapidement son organisation.
* Réutilisabilité : aucun code métier ne doit être dupliqué.
* Testabilité : chaque règle métier doit pouvoir être testée indépendamment.
* Évolutivité : la plateforme doit pouvoir accueillir de nouveaux services (IA, B2B, API, application mobile…).

9.3 Les couches
Je souhaite séparer clairement le projet.
Couche Présentation
Responsable uniquement de l'affichage.
Elle ne contient :
* aucun calcul de prix ;
* aucune logique métier ;
* aucune règle de fabrication.
Elle affiche simplement l'état courant.

Couche Métier
Elle contient toute l'intelligence du configurateur.
Par exemple :
* calcul du prix ;
* validation des dimensions ;
* compatibilité des matériaux ;
* calcul du poids ;
* contraintes de fabrication.
Cette couche ne connaît rien de React.
Elle pourrait fonctionner dans une application mobile.

Couche Données
Responsable de :
* Firebase Auth ;
* Firestore ;
* Storage.
Aucun composant React ne doit appeler directement Firebase.
Toutes les communications passent par des services.

CHAPITRE 21 — Intelligence artificielle
Je pense qu'il faut prévoir cette partie dès aujourd'hui, même si toutes les fonctionnalités ne sont pas développées immédiatement.
Assistant de configuration
Le client peut décrire son besoin :
« Je cherche un écrin pour une bouteille de champagne millésimée avec deux flûtes et une gravure pour un mariage. »
L'IA propose une première configuration.

Recommandations
Pendant la configuration :
« Ce noyer s'accorde particulièrement bien avec cette finition. »
Ou :
« Cette gravure est difficilement lisible avec cette police. »

Analyse des images
Le client télécharge une photo.
L'IA peut :
* détecter l'objet ;
* estimer ses dimensions (avec validation de l'utilisateur) ;
* proposer un compartiment adapté.

Aide à la production
L'IA peut également assister l'artisan :
* vérification des incohérences ;
* détection d'oublis ;
* proposition d'optimisations de fabrication.

Une proposition supplémentaire : le "jumeau numérique"
Chaque configuration deviendrait un véritable jumeau numérique du produit fabriqué.
Cela signifie que le modèle numérique reste associé à l'objet réel tout au long de son cycle de vie :
* conception ;
* devis ;
* fabrication ;
* contrôle qualité ;
* livraison ;
* service après-vente.
Si un client revient trois ans plus tard pour commander un second écrin ou une variante, l'entreprise retrouve instantanément la configuration exacte, son historique, les matériaux utilisés et les éventuelles modifications.


CHAPITRE 22 — Exigences non fonctionnelles
Les exigences non fonctionnelles définissent la qualité attendue du produit. Elles sont aussi importantes que les fonctionnalités.
22.1 Performance
L'utilisateur ne doit jamais avoir l'impression que le site est lent.
Objectifs
* Chargement initial < 2 secondes sur une connexion fibre.
* Affichage de la page d'accueil < 1 seconde (hors chargement des images lourdes).
* Ouverture d'une configuration existante < 3 secondes.
* Sauvegarde automatique < 500 ms (perçue comme instantanée).
* Calcul du prix < 100 ms après une modification.
* Rafraîchissement de la vue 3D < 16 ms (objectif 60 FPS).

22.2 Disponibilité
Le service doit être disponible en permanence.
Objectif :
* disponibilité annuelle ? 99,9 % ;
* aucune perte de configuration en cas de coupure Internet ;
* reprise automatique après reconnexion.

22.3 Sécurité
La sécurité n'est pas une fonctionnalité, c'est une exigence.
Authentification
* Firebase Authentication.
* Connexion par e-mail.
* Connexion Google.
* Connexion Apple (à terme).
* Double authentification pour les administrateurs.

Autorisations
Un client ne peut accéder qu'à :
* ses configurations ;
* ses devis ;
* ses commandes.
Un artisan ne peut accéder qu'aux données nécessaires à son activité.
L'administrateur possède des droits étendus.
Toutes les autorisations sont vérifiées côté serveur (règles Firestore), jamais uniquement côté client.

22.4 Sauvegarde
Toutes les données critiques doivent être sauvegardées.
Une configuration ne doit jamais être perdue.
Même si :
* le navigateur plante ;
* l'ordinateur s'éteint ;
* Internet est coupé.

22.5 Compatibilité
Navigateurs supportés :
* Chrome
* Edge
* Firefox
* Safari
Support mobile :
* iPhone
* Android
* iPad

22.6 Accessibilité
Le site doit respecter les recommandations WCAG 2.2 niveau AA autant que possible.
Par exemple :
* navigation clavier ;
* contrastes suffisants ;
* textes alternatifs ;
* annonces pour les lecteurs d'écran ;
* tailles de police adaptables.

22.7 Observabilité
Chaque erreur importante doit être enregistrée.
Le système devra permettre de répondre à des questions comme :
* Pourquoi cette configuration ne s'est-elle pas sauvegardée ?
* Combien d'erreurs JavaScript ont eu lieu aujourd'hui ?
* Quel est le temps moyen de chargement ?
